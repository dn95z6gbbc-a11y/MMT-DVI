# Архитектура прототипа MMT ДВИ

## Зачем этот файл

Прототип рос итерациями, поэтому до v0.10 загрузчик представлял собой цепочку вложенных `onload` для файлов версий. Это было удобно на раннем этапе, но плохо масштабировалось.

С v0.11 используется manifest-loader в `app.js`: список модулей задаётся одним массивом и загружается последовательно. Это безопасный первый этап рефакторинга — работающие исторические модули пока не переписываются одним большим коммитом.

## Главные общие данные

### `state`

Локальное демо-состояние пользователя. Хранится в `localStorage` через существующий механизм прототипа. Новые функции должны расширять `state`, а не создавать параллельные несвязанные хранилища.

### `window.MMT_UNIVERSITIES`

Единый реестр вузов, введённый в v0.10. Каталог, сравнение, Главная, календарь и новые функции должны читать данные о вузах отсюда.

Правило: не копировать заново город, формат ДВИ, статус кампании, источник и состояние «в плане» в каждом новом модуле.

### `window.MMT_MODULES`

Текущий manifest загружаемых модулей. Нужен для диагностики и постепенной будущей консолидации.

## Функциональные области

- База MMT: новости, репортаж и следующие практические форматы
- Вузы: единый реестр → каталог → сравнение → план → вузовская подготовка
- ДВИ: письменные тренажёры, тестирование, собеседования, симуляции
- Медиасреда: СМИ → журналисты → медиаоблака → 5+5 → регион → повестка
- Портфолио: единый реестр работ → подтверждения → подбор под вуз
- Стажировка: редакции → персональное письмо → статусы обращения
- Календарь: только выбранные вузы + личные события; архивные даты не становятся будущими автоматически

## Правила для следующих версий

1. Не добавлять новые официальные данные без источника/версии кампании.
2. Не дублировать университетские данные вне `MMT_UNIVERSITIES`, если они уже есть в реестре.
3. Новая функциональность должна быть отдельным модулем и по возможности иметь один вход в `state`.
4. Исправления одного модуля лучше вносить в сам модуль, а не бесконечно создавать `-fix`, если это безопасно.
5. Не объединять все старые файлы механически, пока активно меняется UX: риск регрессий выше пользы.
6. После стабилизации ключевых сценариев провести второй этап рефакторинга: выделить общие UI-компоненты, data/store слой и feature-модули перед переносом в Android.

## Что уже сделано в технической уборке v0.11

- вложенная callback-цепочка в `app.js` заменена последовательным manifest-loader;
- появился единый список загружаемых модулей;
- добавлен сигнал `mmt:ready` после успешной загрузки всех модулей;
- каталог/Главная/календарь и новые портфолио/стажировка используют общие данные вместо создания ещё одного набора сведений о вузах;
- зафиксирован план безопасной консолидации до перехода к Android.
